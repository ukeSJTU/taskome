# Secrets via per-service .env, least-privilege SeaWeedFS credentials, HMAC-signed internal webhook

**Service-specific secrets** (DB connection strings, etc.) stay in each service's own `.env`, following the repo's existing convention (already documented in the README for `web`) — no dedicated secrets manager (Vault, Doppler, …). At single-machine scale with a handful of services, that's infrastructure for a problem we don't have yet.

**Shared resources get scoped, not root, credentials**: each Task Server gets its own SeaWeedFS access key/secret, scoped via SeaWeedFS's S3-compatible IAM policies to only its own prefix (e.g. `pepmimic/`) — not one shared root credential across all Task Servers. A bug or compromise in one Task Server can't reach another's stored outputs.

**The Task Server → gateway completion callback (`POST /internal/jobs/{job_id}/complete`, ADR-0005) is a webhook**, and is secured the way webhooks are conventionally secured: the sender computes an HMAC-SHA256 signature of the request body with a shared secret (`X-Taskome-Signature` header) plus a timestamp (`X-Taskome-Timestamp`, rejected if too old, to prevent replay); the gateway recomputes and compares. This doesn't depend on network-level isolation — the gateway is a public-facing entry point (external MCP Agents and the web app both reach it directly), so a route living on the same process/port can't be assumed unreachable from outside without deliberately splitting gateway into a published and an unpublished port, which HMAC signing makes unnecessary: without the shared secret, no valid signature can be produced regardless of network reachability.

We rejected extending better-auth's OAuth/JWT machinery (ADR-0003) to this call: it's designed for end-user identities (web sessions, external Agents), and stretching it to authenticate one internal Python service calling another is solving a problem it wasn't built for, for no real benefit over a standard signed webhook.
