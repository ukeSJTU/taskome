# Three access channels use two Gateway interfaces with channel-specific credentials

Taskome has three Access Channels but only two interfaces: the Web App calls Gateway REST through its BFF, MCP Agents call Gateway MCP directly, and Direct API Clients call Gateway REST directly. All three act for the same User and share Gateway's Job and Input File ownership rules; they do not create separate identities or resource stores. This partially supersedes ADR-0003's "all callers use one JWT verifier," ADR-0012's "Gateway is reachable only from apps/web," and ADR-0019's single-host routing, while preserving Web's BFF boundary and both services' data ownership.

The credentials are deliberately channel-specific. Browser sessions end at apps/web; its BFF presents a short-lived session JWT to Gateway REST. MCP Agents present OAuth access tokens to Gateway MCP. A Direct API Client presents a named Personal API Key in `X-API-Key` to Gateway REST; that key is created, listed, and revoked through the authenticated Web App, is owned and verified by apps/web/Better Auth, and is checked live by Gateway through an internal verification call on every request. Personal API Keys are never accepted by MCP, cannot create other keys, carry their User's full permissions in the first version, and are individually revocable; scopes are deferred until concrete permission boundaries exist.

Configuration distinguishes canonical public identity from internal network reachability with four origins: `BETTER_AUTH_URL`, `WEB_INTERNAL_URL`, `GATEWAY_PUBLIC_URL`, and `GATEWAY_INTERNAL_URL`. Issuers, JWKS and verification paths, REST audience, MCP resource, and OpenAPI server URLs are derived from those origins rather than configured independently. REST session JWTs target `{GATEWAY_PUBLIC_URL}/v1`, MCP OAuth tokens target `{GATEWAY_PUBLIC_URL}/mcp`, and Gateway accepts each only on its matching interface; Docker service addresses are never token audiences.

| Environment                | `BETTER_AUTH_URL`       | `WEB_INTERNAL_URL`      | `GATEWAY_PUBLIC_URL`      | `GATEWAY_INTERNAL_URL`  |
| -------------------------- | ----------------------- | ----------------------- | ------------------------- | ----------------------- |
| Native local development   | `http://localhost:3000` | `http://localhost:3000` | `http://localhost:8000`   | `http://localhost:8000` |
| Production (`example.com`) | `https://example.com`   | `http://web:3000`       | `https://api.example.com` | `http://gateway:8000`   |

The production values above describe the real deployment. The repository's `compose.prod.yml` remains a local production-shape rehearsal and therefore keeps localhost as its public origins while using Docker service names for internal reachability.

Gateway does not implement Personal API Key verification. apps/web exposes a narrow internal transport endpoint that calls Better Auth's server-only `auth.api.verifyApiKey()` and maps its result to the stable fields Gateway needs: whether the key is active, its owning User id, and its key id. Gateway calls this endpoint on every Personal API Key request without caching, so revocation is immediate. The request uses ADR-0009's timestamped HMAC-SHA256 internal-request pattern, but with a distinct Web↔Gateway secret rather than any Task Server↔Gateway webhook secret or `BETTER_AUTH_SECRET`; the protocol is shared while each trust relationship keeps its own blast radius. Missing, invalid, revoked, or expired credentials produce `401`; future insufficient-scope failures produce `403`; verifier unavailability produces `503`; and attempts to access another User's resource produce `404` to avoid disclosing its existence.

Personal API Keys use Better Auth's user-owned API Key plugin with a fixed `taskome_` prefix, required name, default `X-API-Key` header, hashing enabled, no expiration, no permissions, and API-key-to-session mocking disabled. The plugin's generic per-key rate limiter is explicitly disabled—its default of ten requests per day is incompatible with polling, and request-cost and compute limits belong in Gateway rather than credential verification. Better Auth's own endpoint rate limiting may still protect login and other authentication handlers independently in future. Verification also confirms that the referenced User still exists and is allowed to authenticate, so deleting or later disabling a User immediately invalidates every key they own. Key creation uses Better Auth's normal valid-session requirement in the first version; recent re-authentication is deliberately deferred. The product calls permanent invalidation **Revoke**, not Delete.

Gateway authentication adapters normalize every successful credential into one immutable Principal containing only the canonical User id, credential kind (`session_jwt`, `oauth_access_token`, or `personal_api_key`), and an optional credential id (OAuth `azp` client id or Personal API Key id). REST dependencies, MCP tools, `/v1/me`, and structured logging consume this Principal instead of parsing headers, JWT claims, or Better Auth responses themselves. The Principal is bound to request-scoped structured-log context so access and domain-event logs carry User and non-secret credential identity; raw tokens, API keys, signatures, presigned query strings, and verifier bodies are never logged. Durable append-only audit storage is deferred until a real retention or compliance requirement exists.

Revoking a Personal API Key irreversibly sets it disabled rather than physically deleting its record. This preserves the key id and non-secret metadata needed to interpret historical logs; revoked keys cannot be re-enabled. The Web UI may show revoked history separately from active keys.

Production routing uses one existing Gateway deployment, not separate REST and MCP deployables: `example.com` routes to apps/web, `docs.example.com` to apps/docs, and `api.example.com` routes `/v1/*` to Gateway REST, `/mcp` to Gateway MCP, and the required protected-resource discovery paths to Gateway; all other Gateway paths remain unavailable at the public edge. The public API does not enable CORS initially, so browser UI code continues to use the BFF while non-browser clients use the public REST endpoint.

MCP authorization initially exposes one coarse `taskome` scope representing the User's complete MCP capability; it will be split only when real permission boundaries are designed. This is distinct from Personal API Keys, which carry no scopes in the first version.

For client onboarding, Better Auth 1.6.26 does not support the current MCP specification's preferred Client ID Metadata Documents, so the authorization server enables unauthenticated OAuth Dynamic Client Registration as a standards-based compatibility fallback. Anonymous registration can create only public authorization-code clients: no client credentials grant, exact registered redirect URI checks, PKCE S256, and explicit User login and consent remain mandatory; Better Auth's production registration rate limit remains enabled. When the dependency supports Client ID Metadata Documents, add that preferred mechanism while retaining DCR only as a compatibility fallback.

`/v1` is the complete user-facing Gateway REST contract used by both the BFF and Direct API Clients. Service-to-service operations live under `/internal`; health, MCP, auth, and development endpoints are not part of the user REST contract. REST requests present exactly one credential mechanism: a session Bearer JWT or a Personal API Key; presenting both is rejected with `400 Ambiguous credentials`, with no precedence or fallback. An authenticated `/v1/me` operation reports the canonical User identity and credential kind, plus the key id for a Personal API Key, as an authentication diagnostic; its exact JSON shape is intentionally left to the API design rather than fixed here. Gateway generates a dynamic Public OpenAPI projection from all and only `/v1` operations, with API-key authentication and the public server URL. The full/internal schema declares session Bearer JWT and Personal API Key as alternative REST mechanisms, while the Public projection shows only the Personal API Key mechanism relevant to Direct API Clients. The authenticated Scalar React page in apps/web serves that projection through a same-origin BFF endpoint that fetches it from the running Gateway, so user documentation matches the deployed service without opening CORS. Gateway's full checked-in OpenAPI document remains the source for Orval and development tooling, preserving ADR-0012's build-time independence while superseding ADR-0021's requirement that the user reference render that same checked-in document.
