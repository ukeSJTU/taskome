# `packages/task-kit`: a real shared library for Task Server REST+MCP wiring, not a bare interface

Every Task Server needs the same REST+MCP wiring around a completely different piece of compute logic (see ADR-0017 for the port/adapter shape that wiring is built around). A bare `Protocol` with no shared implementation was considered and rejected: it would let every Task Server's adapter _look_ the same from the outside, but the actual FastAPI routing, fastmcp tool registration, error-to-response mapping, and workdir lifecycle code would still be hand-written per Task Server — exactly the "redesign the comms interface per tool" duplication we're trying to avoid. `packages/task-kit` exists to hold that shared implementation, not just a shared name.

fpocket is being built first specifically so this library's design gets forced through the harder case (an external CLI binary called via subprocess) before pdb-tools (a pure-Python, in-process case) is added second — a concretely planned, near-term second consumer, not a hypothetical one. That distinguishes this from ADR-0010's "no shared `packages/observability` yet" call: that extraction was deferred because there was no second consumer in sight; here there are two Task Servers on the near-term roadmap from the start, and even for the first one alone, routing the compute call through an injectable port (ADR-0017) is what makes the REST/MCP plumbing testable without needing the real `fpocket` binary.

**Location and workspace membership**: `packages/task-kit`, plain Python, no `package.json` — `pnpm-workspace.yaml` enumerates member paths explicitly rather than globbing, so simply not listing it there is sufficient; no exclusion rule is needed. It _is_ added to the root `pyproject.toml`'s `[tool.uv.workspace].members`, alongside `apps/gateway` — unlike a Task Server (ADR-0001/0015), it's our own library code with no independent deployment, so it doesn't need the dependency/lockfile isolation those get. It has its own minimal `mise.toml` (`lint`/`format`/`check`/`test` only, no `dev`/`start`, since it's a library, not a service), registered in the root `mise.toml`'s `[monorepo].config_roots`, matching the existing `apps/gateway` pattern.

**Toolchain clarification** (this took a wrong turn mid-design and is worth recording precisely): the root `pyproject.toml`'s `[tool.ruff]`/`[tool.ty]` config applies by file-path glob (`extend-exclude = ["references"]`, `[tool.ty.src] exclude = [...]`), which is entirely independent of `[tool.uv.workspace].members`. Lint/typecheck coverage never required workspace membership — it applies to any first-party Python source not explicitly excluded, regardless of which `pyproject.toml` governs its dependency resolution. This means "unified toolchain" and "isolated dependency resolution" aren't in tension and don't have to be traded off against each other, for `packages/task-kit` or for any Task Server: a Task Server's `compute/` directory only needs adding to the exclude list (same treatment as `references`) if it ever contains vendored Python source; a compiled-binary `compute/` (e.g. fpocket's C source) is already invisible to `.py`-scoped tools with no config change at all.
