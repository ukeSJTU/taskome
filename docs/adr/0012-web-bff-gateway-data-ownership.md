# apps/web is the sole BFF; it and apps/gateway each own their own data and never touch the other's Postgres tables directly

apps/web and apps/gateway are the only two deployables in this repo — there is no separate frontend/backend split of apps/web. apps/web is a single Next.js app: its React UI (dashboard, auth pages, and eventually a public/SEO landing page) and its own Next.js API routes are one deployment unit. That Next.js API layer is the BFF: today it only serves better-auth's endpoints, but it will grow to aggregate calls to apps/gateway's REST API into responses shaped for the frontend. apps/gateway remains the separate service described in ADR-0001–0011: it owns business APIs and Job/Input File state, and exposes both REST (for the web BFF) and MCP (for external agents).

**Ownership boundary**: each service reads and writes only the Postgres data it owns. apps/web owns the auth tables (and, if ever needed, purely presentational config with no cross-domain meaning); apps/gateway owns everything else — jobs, input file metadata, and future business tables. Neither queries the other's tables directly; all cross-service access goes through gateway's REST API, authenticated the same way as any other caller (ADR-0003). This generalizes the pattern ADR-0003 (gateway never touches the `user`/`session` tables, only verifies JWTs) and ADR-0010 (web will read job status through gateway's REST API, not Postgres) already established for two specific cases into one rule.

**Postgres stays one shared instance** (per ADR-0008's single-machine deployment), split into a schema per owner — a `gateway` schema alongside the existing auth tables — for readability, not enforcement. Enforcing the boundary via Postgres roles/grants was considered and deferred: the ownership rule above is carried by convention and code review for now, revisit if it's ever violated in practice.

**Migration tooling stays per-owner too**: `packages/db` (Drizzle) continues to own only the auth schema; apps/gateway will manage its own schema with SQLAlchemy + Alembic once it has tables to migrate. The two never share migration state — there's no TypeScript/Python bridge to build, and Alembic is the standard pairing for a Python service that doesn't already depend on Drizzle.

**How the BFF calls gateway**: apps/gateway is reachable only from apps/web's server side — never from the browser — so `GATEWAY_URL` is a server-only env var. Every call carries a short-lived JWT that better-auth's `jwt` plugin mints for the current session, sent as `Authorization: Bearer <token>` — the web-app side of the JWT flow ADR-0003 already specified but hadn't wired up. The client itself is generated by orval from gateway's OpenAPI spec (exported to a static, checked-in `openapi.json` rather than fetched from a running instance, so generating the TS client never requires a live Python process) and lives in a new package, `packages/api-client`. A custom orval mutator inside that package attaches the JWT to every request, so call sites never handle tokens directly; the package imports Next.js's `server-only` to fail loudly if it's ever pulled into a client component.

## Considered and rejected

- **Splitting apps/web into separate frontend and backend deployables** — the trigger for this discussion, but nothing about SEO/landing pages or the future data API requires a second deployment unit; Next.js already serves both server-rendered pages and API routes from one app.
- **Enforcing the ownership boundary with Postgres roles/grants now** — real isolation, but more setup than today's requirement justifies for a single small team; convention is enough until it's actually violated.
- **orval fetching gateway's OpenAPI spec from a running instance** — would make generating `packages/api-client`'s types depend on a live Python process; a checked-in static spec keeps the TS toolchain self-contained.
- **Hand-written fetch calls instead of a generated client** — apps/web (TypeScript) and apps/gateway (Python) share no types; hand-written calls drift from the actual contract with nothing to catch it.

## Consequences

- `packages/api-client` needs a script (and a reminder in its README, or a CI check) to keep the checked-in `openapi.json` in sync with apps/gateway's actual routes — not enforced by this ADR, just noted as the cost of the static-spec choice.
- `packages/auth`'s `betterAuth()` config needs the `jwt` plugin added — it isn't there yet.
- apps/gateway owns the fixed `gateway` schema through SQLAlchemy and Alembic. Its migration history is independent of Drizzle's `public` schema history, and the production Compose migration job applies Gateway revisions before the application starts.
