# Large user-provided input files (PDB and future types) transfer via gateway-issued presigned SeaweedFS URLs

Designed ahead of implementation, across two design passes — nothing in `apps/gateway` or any `apps/task-*` exists yet to build this against. Treat the mechanics below (endpoint shapes, exact checks) as the settled _shape_ of the design, open to adjustment only once real implementation surfaces details neither pass could see; update this ADR (or supersede it) rather than silently drifting from it.

MCP Agents and the web app both need to supply large binary files (e.g. user PDB structures) as Task inputs without embedding raw bytes in a tool_call. The gateway's external-facing MCP endpoint is HTTP-based — ADR-0003's JWT/JWKS bearer-token auth model presupposes a network transport, and ADR-0007's internal Task Server aggregation is built entirely on HTTP-mode `mount()`/proxy — so there's no local filesystem to pass a path to the way a stdio-transport MCP server would have; embedding content instead forces the calling agent to emit the entire file as generated text, which is both context-expensive and error-prone. The gateway instead exposes a shared, Task-agnostic capability that mints a short-lived presigned SeaweedFS PUT URL; the caller's own environment performs the byte transfer out-of-band (never through the model's context), and only an opaque `Input File` id is passed into subsequent Task tool calls. The PUT URL is signed with the `If-None-Match: *` condition, which callers must send, so the first successful PUT makes the object's bytes immutable for that id. Job outputs (already in SeaweedFS per ADR-0004) are exposed back to callers the same way — a presigned GET URL included directly in the Job status/result response — rather than raw content or a second bespoke mechanism.

This capability is exposed twice, over one shared internal implementation, rather than being MCP-only: a Task-agnostic MCP tool for external Agents, and a REST endpoint (`POST /v1/input-files` for upload, plus a download-URL and a delete endpoint) that apps/web's BFF (ADR-0012) calls server-side on behalf of a logged-in user. Both are thin adapters over the same gateway-internal mint/validate/delete logic — the same shared-core pattern ADR-0002 established for Task Servers, applied here to the gateway itself. The web app's browser client receives only the presigned URL from its own server (never a raw SeaweedFS credential) and performs the PUT/GET directly against SeaweedFS, exactly like an external MCP Agent does — proxying file bytes through the Next.js server as a third hop would add latency and memory/timeout pressure for no benefit, and the gateway would otherwise end up implementing the same mint logic twice.

`Input File` is modeled as its own entity, independent of any Job: a user uploads once and may reference it across multiple Jobs/Tasks. It lives in a dedicated SeaweedFS prefix owned by the gateway's own scoped credential — distinct from any Task Server's own output prefix (ADR-0009) — so an Input File's existence and ownership don't depend on which Task eventually consumes it (exact key shape below). Every mint call issues a brand-new id; there is no "re-PUT to an existing id" operation, so an Input File's bytes are immutable for the lifetime of that id — a corrected re-upload always produces a new Input File, and old references keep pointing at the old bytes rather than silently changing underneath them. There's no upload-completion webhook: the gateway validates an Input File lazily (a single existence check) the first time its id is referenced, e.g. at Job creation, since nothing is otherwise waiting on that state transition the way Job completion drives queue/polling logic (ADR-0005). That check only proves the file existed at Job-creation time, not that it will still exist whenever a queued Job is eventually picked up — an accepted gap (see the Task Server retrieval paragraph below), not a silent assumption.

When a Job actually runs, the Task Server needs the real bytes on local disk for its subprocess — but per ADR-0009's least-privilege scoping, it has no standing credential for the gateway's `uploads/` prefix. Rather than widening any Task Server's IAM footprint, the Task Server calls a gateway-internal endpoint to fetch a fresh, short-lived presigned GET URL **immediately before it starts the subprocess** — not baked into the Taskiq dispatch payload at enqueue time. ADR-0005's dispatch is durable specifically so a Job can sit queued for an unbounded stretch (Task Server downtime, backlog, jobs already run "minutes to multiple hours, with no fixed upper bound"), so a URL minted at enqueue time would routinely be expired by the time it's actually used; minting it at the moment of use ties its freshness to the moment it's needed, regardless of queue delay — and if the Input File has since been deleted, that GET simply fails the Job, which is an acceptable, visible failure mode rather than a silent one. This call is secured the same way as the existing Task Server → gateway direction (ADR-0009's `/internal/jobs/{job_id}/complete` webhook): HMAC-signed with a shared secret plus a timestamp, not bare network reachability. The gateway additionally checks that the requested `input_file_id` is actually the one attached to the Job this Task Server was dispatched to run — not just any id the caller happens to supply — since an unguessable id alone stops blind enumeration but not a request that's never checked against the calling context. The Task Server streams the bytes from that URL to a fixed, server-controlled local path — never the Input File's user-supplied original filename (see below) — and never holds a SeaweedFS credential of its own for this path.

Storage keys are deliberately ownership-agnostic: an Input File lives at `uploads/{inputFileId}` (an unguessable id, e.g. UUID v4) with no owner or filename segment in the path. The owning user and original filename are plain columns on the Input File's database record, never trusted as path components — the original filename is arbitrary caller-supplied text and is only ever used for display (e.g. a download's `Content-Disposition` header, sanitized at render time) or as an extension hint for the Task Server's adapter layer, never as an on-disk path, which closes off path traversal via a crafted filename like `../../etc/x`. The gateway checks ownership at every access point (minting a download URL, resolving an `input_file_id` referenced at Job creation, deleting) — the object's physical location never encodes who owns it. This isn't a stylistic choice: unlike Task Servers (ADR-0009), where distinct credentialed services genuinely need IAM-enforced blast-radius isolation from each other, only the gateway itself ever holds an `uploads/` credential — end users never get SeaweedFS credentials directly, only gateway-issued presigned URLs scoped to one object after an application-level authorization check. A `{userId}` path segment would therefore have bought no IAM-enforced isolation, only the appearance of it, while baking the ownership model into the storage layer — so a future change to that model (e.g. adding organization-level ownership) would require physically copying objects (S3 has no atomic rename) instead of a plain database migration.

Gateway config carries two SeaweedFS S3 endpoints, not one: an internal endpoint (docker-network address) used for the gateway's own direct S3 calls, and a public endpoint used only when generating presigned URLs handed to external callers (browsers, MCP Agents). `infra/proxy/` has no real deployment target yet (placeholder, per its README), so today the public endpoint defaults to the same dev-reachable address as the internal one — but the config seam exists now so that wiring in a real public hostname later is a config change, not an API-shape change.

The gateway supports explicit, user-initiated deletion of an Input File, not just the (still out-of-scope) automatic garbage collection discussed below. Delete is a soft delete: the gateway marks the database row `deleted_at`, deletes the underlying SeaweedFS object, and leaves the row itself in place so Jobs that already referenced this Input File can still show its original filename/metadata in history instead of resolving to a dangling id. A soft-deleted Input File fails the same existence/ownership checks as one that never existed, at every access point. Deletion does not currently check whether a non-terminal (`queued`/`running`) Job still references the id — the correct behavior is to refuse deletion in that case, but the query to find non-terminal Jobs referencing an Input File isn't buildable yet (Job creation/state isn't implemented). This is tracked as a `TODO` at the delete call site, not silently skipped: until it's wired up, deleting an Input File that a queued Job depends on produces the same accepted, visible failure at fetch time described above for a file deleted mid-queue.

## Considered and rejected

- **Embedding file content directly in tool_call arguments** — forces the agent to emit the full byte content as generated text; expensive and error-prone at any real file size.
- **MCP `resources` primitive** — solves discovery/addressing of server-exposed content, not out-of-band binary transport; reading a resource still delivers its content through the same context-bearing channel, so it doesn't address the original problem.
- **Proxying upload/download bytes through the Next.js BFF instead of a direct browser↔SeaweedFS presigned transfer** — mirrors the MCP embedding problem in a different shape: an extra hop through the Next.js server adds latency and memory/timeout pressure for large files, and duplicates mint logic that already exists for the MCP path.
- **Granting each Task Server IAM read access to the gateway's `uploads/` prefix** — works, but widens every Task Server's blast radius for a capability (reading arbitrary uploaded files) it only ever needs one specific file from, once, per Job — a presigned per-Job URL is equivalently simple to plumb without the standing grant.
- **Baking the presigned GET URL into the Taskiq dispatch payload at enqueue time** — breaks under ADR-0005's own durability guarantee: a Job can sit queued for an unbounded time, so a URL minted at enqueue would often be expired before the Task Server actually fetches it.
- **Namespacing storage keys by owner (`uploads/{userId}/...`)** — mirrors ADR-0009's Task Server pattern without the matching threat model (no second credential holder to isolate from), while coupling the storage layer to an ownership model that's expected to change (individual users today, organizations later).
- **Hard-deleting an Input File on user request** — loses the original filename/metadata for any Job that already referenced it, turning Job history into a dangling reference instead of a resolvable-but-gone one; soft delete costs one nullable column.
- **Restricting uploads to an extension/MIME allowlist at mint time** — CONTEXT.md deliberately defines Input File broadly (not narrowed to "Structure," to leave room for future non-structure input types); type suitability is a concern for whichever Task consumes the file, not the gateway's generic storage layer.

## Consequences

- Task Servers never hold SeaweedFS credentials for anything outside their own output prefix.
- Multipart upload is not implemented yet — SeaweedFS supports it identically to AWS S3 if a real input file ever needs it; a single presigned PUT is simpler and sufficient for today's PDB-sized files. No explicit maximum-size cap is enforced yet either, at the application layer or via any reverse-proxy body-size limit (`infra/proxy/` has no real deployment target to verify against) — this is left as a `TODO` at the mint call site rather than guessed at now.
- The shared upload-request capability (both the MCP tool and the REST endpoint) is authenticated exactly like every other gateway entry point — the same JWT verification as ADR-0003, with no exception carved out for it being new. The new Task Server → gateway retrieval endpoint instead reuses ADR-0009's HMAC-signed internal-webhook pattern and binds the request to the calling Task Server's own dispatched Job, since it's the same service-to-service direction ADR-0009 already covers, not an end-user-facing call.
- Adding organization-level ownership later is a database-only change (new/changed owner column, migrate ownership pointers) — the storage layer never has to move an object because of it.
- Orphaned Input File rows from abandoned or retried upload requests are still out of scope — no TTL/reaper exists. This is an explicit, revisit-if-it-becomes-a-real-problem deferral, not a gap that was overlooked.
- User-initiated delete is soft delete (`deleted_at` + SeaweedFS object removal, DB row retained); blocking delete while a non-terminal Job references the Input File is deferred behind a `TODO` until Job querying exists, so deletion is currently unconditional.
- Gateway config gains an internal/public SeaweedFS endpoint split ahead of any real `infra/proxy/` target existing, so that decision doesn't force an API-shape change later.
