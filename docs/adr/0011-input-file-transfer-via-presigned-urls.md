# Large user-provided input files (PDB and future types) transfer via gateway-issued presigned SeaweedFS URLs

Designed ahead of implementation — nothing in `apps/gateway` or any `apps/task-*` exists yet to build this against. Treat the mechanics below (endpoint shapes, exact checks) as the settled _shape_ of the design, open to adjustment once real implementation surfaces details this session couldn't see; update this ADR (or supersede it) rather than silently drifting from it.

MCP Agents must supply large binary files (e.g. user PDB structures) as Task inputs without embedding raw bytes in a tool_call. The gateway's external-facing MCP endpoint is HTTP-based — ADR-0003's JWT/JWKS bearer-token auth model presupposes a network transport, and ADR-0007's internal Task Server aggregation is built entirely on HTTP-mode `mount()`/proxy — so there's no local filesystem to pass a path to the way a stdio-transport MCP server would have; embedding content instead forces the calling agent to emit the entire file as generated text, which is both context-expensive and error-prone. The gateway instead exposes a shared, Task-agnostic MCP tool that mints a short-lived presigned SeaweedFS PUT URL; the caller's own environment performs the byte transfer out-of-band (never through the model's context), and only an opaque `Input File` id is passed into subsequent Task tool calls. Job outputs (already in SeaweedFS per ADR-0004) are exposed back to Agents the same way — a presigned GET URL included directly in the Job status/result response — rather than raw content or a second bespoke mechanism.

`Input File` is modeled as its own entity, independent of any Job: a user uploads once and may reference it across multiple Jobs/Tasks. It lives in a dedicated SeaweedFS prefix owned by the gateway's own scoped credential — distinct from any Task Server's own output prefix (ADR-0009) — so an Input File's existence and ownership don't depend on which Task eventually consumes it (exact key shape below). There's no upload-completion webhook: the gateway validates an Input File lazily (a single existence check) the first time its id is referenced, e.g. at Job creation, since nothing is otherwise waiting on that state transition the way Job completion drives queue/polling logic (ADR-0005). That check only proves the file existed at Job-creation time, not that it will still exist whenever a queued Job is eventually picked up — an accepted gap (see the Task Server retrieval paragraph below), not a silent assumption.

When a Job actually runs, the Task Server needs the real bytes on local disk for its subprocess — but per ADR-0009's least-privilege scoping, it has no standing credential for the gateway's `uploads/` prefix. Rather than widening any Task Server's IAM footprint, the Task Server calls a gateway-internal endpoint to fetch a fresh, short-lived presigned GET URL **immediately before it starts the subprocess** — not baked into the Taskiq dispatch payload at enqueue time. ADR-0005's dispatch is durable specifically so a Job can sit queued for an unbounded stretch (Task Server downtime, backlog, jobs already run "minutes to multiple hours, with no fixed upper bound"), so a URL minted at enqueue time would routinely be expired by the time it's actually used; minting it at the moment of use ties its freshness to the moment it's needed, regardless of queue delay — and if the Input File has since been deleted, that GET simply fails the Job, which is an acceptable, visible failure mode rather than a silent one. This call is secured the same way as the existing Task Server → gateway direction (ADR-0009's `/internal/jobs/{job_id}/complete` webhook): HMAC-signed with a shared secret plus a timestamp, not bare network reachability. The gateway additionally checks that the requested `input_file_id` is actually the one attached to the Job this Task Server was dispatched to run — not just any id the caller happens to supply — since an unguessable id alone stops blind enumeration but not a request that's never checked against the calling context. The Task Server streams the bytes from that URL to a fixed, server-controlled local path — never the Input File's user-supplied original filename (see below) — and never holds a SeaweedFS credential of its own for this path.

Storage keys are deliberately ownership-agnostic: an Input File lives at `uploads/{inputFileId}` (an unguessable id, e.g. UUID v4) with no owner or filename segment in the path. The owning user and original filename are plain columns on the Input File's database record, never trusted as path components — the original filename is arbitrary caller-supplied text and is only ever used for display (e.g. a download's `Content-Disposition` header, sanitized at render time) or as an extension hint for the Task Server's adapter layer, never as an on-disk path, which closes off path traversal via a crafted filename like `../../etc/x`. The gateway checks ownership at every access point (minting a download URL, resolving an `input_file_id` referenced at Job creation) — the object's physical location never encodes who owns it. This isn't a stylistic choice: unlike Task Servers (ADR-0009), where distinct credentialed services genuinely need IAM-enforced blast-radius isolation from each other, only the gateway itself ever holds an `uploads/` credential — end users never get SeaweedFS credentials directly, only gateway-issued presigned URLs scoped to one object after an application-level authorization check. A `{userId}` path segment would therefore have bought no IAM-enforced isolation, only the appearance of it, while baking the ownership model into the storage layer — so a future change to that model (e.g. adding organization-level ownership) would require physically copying objects (S3 has no atomic rename) instead of a plain database migration.

## Considered and rejected

- **Embedding file content directly in tool_call arguments** — forces the agent to emit the full byte content as generated text; expensive and error-prone at any real file size.
- **MCP `resources` primitive** — solves discovery/addressing of server-exposed content, not out-of-band binary transport; reading a resource still delivers its content through the same context-bearing channel, so it doesn't address the original problem.
- **Granting each Task Server IAM read access to the gateway's `uploads/` prefix** — works, but widens every Task Server's blast radius for a capability (reading arbitrary uploaded files) it only ever needs one specific file from, once, per Job — a presigned per-Job URL is equivalently simple to plumb without the standing grant.
- **Baking the presigned GET URL into the Taskiq dispatch payload at enqueue time** — breaks under ADR-0005's own durability guarantee: a Job can sit queued for an unbounded time, so a URL minted at enqueue would often be expired before the Task Server actually fetches it.
- **Namespacing storage keys by owner (`uploads/{userId}/...`)** — mirrors ADR-0009's Task Server pattern without the matching threat model (no second credential holder to isolate from), while coupling the storage layer to an ownership model that's expected to change (individual users today, organizations later).

## Consequences

- Task Servers never hold SeaweedFS credentials for anything outside their own output prefix.
- Multipart upload is not implemented yet — SeaweedFS supports it identically to AWS S3 if a real input file ever needs it; a single presigned PUT is simpler and sufficient for today's PDB-sized files. Any reverse-proxy body-size limit in front of the presigned PUT still needs verifying against real file sizes before launch — a deployment-config concern, not an architectural one.
- The shared upload-request tool is authenticated exactly like every other gateway entry point — the same JWT verification as ADR-0003, with no exception carved out for it being new. The new Task Server → gateway retrieval endpoint instead reuses ADR-0009's HMAC-signed internal-webhook pattern and binds the request to the calling Task Server's own dispatched Job, since it's the same service-to-service direction ADR-0009 already covers, not an end-user-facing call.
- Adding organization-level ownership later is a database-only change (new/changed owner column, migrate ownership pointers) — the storage layer never has to move an object because of it.
- Orphaned Input File rows from abandoned or retried upload requests are out of scope here, same as the upload garbage-collection policy already deferred earlier in this design session — not a gap unique to this ADR.
