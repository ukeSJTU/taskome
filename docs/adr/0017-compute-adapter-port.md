# `ComputeAdapter` is a Ports & Adapters port; `register_task` is the one place REST and MCP wiring gets generated from it

`packages/task-kit` (ADR-0016) needs a seam between "how a Task's compute logic gets invoked" (different per tool: subprocess for a CLI binary, direct call for in-process Python) and "how a Task gets exposed over REST and MCP" (identical machinery for every tool). We deliberately adopt Ports & Adapters (hexagonal architecture) for this: `ComputeAdapter[ParamsT, ResultT]` is a generic `Protocol` with one method, `run(self, params: ParamsT, ctx: RunContext) -> ResultT` — the port. Each Task Server supplies one concrete adapter (e.g. `FpocketAdapter`, wrapping `subprocess.run()`); tests supply a Fake instead. This isn't a novel pattern invented for this problem — it's the standard answer to "swap an external dependency for a test double behind a stable interface," picked because our shape (many independently-deployed services, each needing an environment-isolated compute step that must be fakeable in tests) is exactly the case it's for. `references/biomcp` (a related real-world MCP server) doesn't use an equivalent trait/port, but that's because its compute is dozens of in-process HTTP client calls inside one Rust binary with no environment isolation to speak of — a different problem shape, not evidence against this one.

`task-kit` exposes `register_task(app: FastAPI, mcp: FastMCP, *, name, params_model: type[ParamsT], result_model: type[ResultT], adapter: ComputeAdapter[ParamsT, ResultT])`. It generates one REST route and registers one `mcp.tool`, both ultimately running the same sequence: validate params → create a workdir → call `adapter.run()` → map any `ComputeError` to a response → package the result. This is the concrete payoff of ADR-0016 — without it, every Task Server hand-writes near-identical REST and MCP glue around its own adapter. A single Pydantic model can drive both a FastAPI request body and an `@mcp.tool` parameter (fastmcp 4.0.0b2 derives its schema from function-signature introspection the same way FastAPI does), so `params_model`/`result_model` don't need separate REST and MCP variants. We deliberately did **not** add an `execution_mode` parameter as a placeholder for future async support — this is an internal API with no compatibility surface to protect, so a signature change later is cheap, and a parameter with exactly one legal value today carries no information.

**`RunContext`, not a bare `workdir: Path`.** `run()`'s second argument bundles `workdir: Path`, a `structlog` logger (wired to ADR-0010's tracing), and `timeout_seconds: float`. Anything else every adapter will eventually need (e.g. a cancellation token) becomes a new `RunContext` field, not a new positional argument on every adapter's `run()`.

**Timeout enforcement is split, and the split matters for correctness, not just style.** `task-kit` supplies the timeout _budget_ via `RunContext.timeout_seconds`, but cannot enforce it centrally: `adapter.run()` is a blocking call, almost certainly dispatched to a worker thread, and Python cannot forcibly kill a running thread from outside. Wrapping the call in an `asyncio`/`anyio` timeout would let the request return on schedule while the thread — and any subprocess it spawned — keeps running as an orphan. The adapter itself must therefore pass the budget into its own blocking call (e.g. `subprocess.run(..., timeout=ctx.timeout_seconds)`, which lets `subprocess` deliver the `SIGKILL`). This is a required part of implementing the port, not an optional nicety.

**`ComputeError` is a small hierarchy, provisionally three classes**: `ComputeError` (base) → `ComputeInputError` (bad input/params, maps to a 4xx-shaped REST response and an MCP invalid-params-style error), `ComputeTimeoutError`, `ComputeExecutionError` (environment/infrastructure failure, maps to REST 500). `register_task`'s generated handler catches these specific types and maps each to a different response instead of collapsing every failure into a generic 500; adapters raise whichever fits the failure they observed. Whether three classes is the right grain (e.g. whether "params the model accepted but the tool itself rejected" needs to be distinguished from "params that failed model validation") is still open — treat this split as a starting point, not a closed decision.

**Workdir lifecycle is task-kit's job.** `register_task`'s generated handler creates the workdir and deletes it in a `finally`, regardless of whether `adapter.run()` succeeds, raises a `ComputeError`, or raises anything else. Adapter authors never implement cleanup.

**v1 has no object storage, so output files travel inline — a temporary constraint, not a design decision to preserve.** ADR-0011's presigned-URL flow is gateway-owned and out of scope until gateway integration lands (this Task Server is built and tested standalone first). Until then, a `ComputeResult`'s output files must be embedded directly in the response body (e.g. base64-encoded) rather than referenced by a workdir-local path, which is meaningless to a remote caller and gone by the time the response is read anyway. Expect this to be replaced by presigned-URL-based upload once the Task Server integrates with gateway's storage.

**Params stay curated, with no `extra_args` passthrough.** A Task's `params_model` remains a curated subset of the wrapped tool's real configuration surface (AGENTS.md's existing direction), not a 1:1 mapping of every upstream CLI flag. We explicitly rejected an `extra_args: list[str]` escape hatch for uncurated flags: the adapter's job is to translate the wrapped tool's raw CLI/file vocabulary into our own clean domain types — an anti-corruption layer — and a raw-passthrough field defeats that translation for exactly the inputs it would be used for, while also reopening the injection and traceability problems the curated model exists to avoid. This applies to every Task, not just fpocket.
